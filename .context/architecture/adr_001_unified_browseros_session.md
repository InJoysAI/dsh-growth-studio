# ADR-001: 统一 BrowserOS 实例管理会话（否决日用 Chrome Cookie 探取）

**状态**: Accepted
**日期**: 2026-10-15（源文档 v1.2.0）
**决策者**: N/A – 源文档未提供

---

## 上下文 (Context)

工作台需要在执行草稿预填**之前**判断用户在各平台是否已登录，以便在驾驶舱显示平台就绪状态、并在未登录时引导登录。

原设计方案试图从日常使用的 Chrome 的 SQLite 数据库（`~/.config/google-chrome/Default/Cookies`）探测 Cookie，据此判定登录态。

**当前面临什么问题？**

该方案在静态评审与源码分析后暴露出**三大根本问题**，使其无法成立：

1. **实例不一致** —— 日用 Chrome 与 BrowserOS MCP 是两个**完全不同**的浏览器环境与用户目录。在 Chrome 探测到 Cookie **根本不能保证** BrowserOS 执行预填时已登录，导致工作台呈现"就绪"**假象**；
2. **SQLite WAL 不完整** —— 直接复制 `Cookies` 主文件未同步拷贝 `Cookies-wal` 与 `Cookies-shm`。当 Chrome 处于活跃写状态时，容易**漏检最新 Cookie**；
3. **隐私与安全** —— 拷贝并挂载整个 SQLite 库会使**所有个人 Cookie 进入内存**，与"仅存在性探测"的隐私承诺存在**落差**。

---

## 决策驱动因素 (Decision Drivers)

- **正确性**：探测结果必须真实反映**执行预填的那个浏览器实例**的登录态
- **隐私承诺**：会话数据零外发、仅做存在性/状态判定
- **实现成本**：避免处理 SQLite WAL/SHM 的复制一致性问题
- **假阳性危害**：假就绪会让用户在预填失败后才发现问题，浪费一轮操作

---

## 备选方案 (Considered Options)

### 方案 A: 从日用 Chrome 的 SQLite Cookie 库探测（原方案）

**描述**：定位 `~/.config/google-chrome/Default/Cookies`，复制并查询其中的 Cookie 记录。

**优点**:
- 无需启动浏览器即可探测
- 覆盖面广（用户在日用浏览器中已登录的平台）

**缺点**:
- **实例不一致** → 探测到的登录态与 BrowserOS 实例无关，产出**假阳性**
- **WAL 不完整** → 漏检最新 Cookie，结果不可靠
- **隐私落差** → 整个 SQLite 库进入内存，与"仅存在性探测"承诺不符
- 需处理跨平台路径与 Chrome 变体差异

### 方案 B: 统一 BrowserOS 实例 + 轻量探测（**采用**）

**描述**：登录态探测、草稿箱预填与大屏指标采集**统一由同一个 BrowserOS MCP 实例调度**。`SessionGuard` 通过 BrowserOS MCP 查询当前活跃 Tab 或后台导航至目标平台验签 URL（如微信后台与 B站创作平台），通过页面特征或网络响应判定会话状态，返回四态。

**优点**:
- **探测与执行是同一个实例** → 结果真实，**杜绝假阳性**
- **隐私友好** → 只做状态判定，不导出 Cookie 内容；会话留在本地沙箱
- 与预填共享同一套 BrowserOS 连接与能力开关，无额外基础设施
- 四态语义可表达"已登录但无发布权限"这类中间情况

**缺点**:
- 需要 BrowserOS 实例处于可访问状态（未启动时只能返回 `unknown`）
- 探测有延迟（需导航或查询 Tab）

### 方案 C: 不做会话探测，仅在实际预填时暴露错误

**描述**：驾驶舱不显示就绪状态，用户点击预填时才知道是否登录。

**优点**:
- 实现最简单，零探测成本

**缺点**:
- 驾驶舱失去关键信息，"哪些平台可发"不可见
- 用户体验差：预填失败后才发现未登录

---

## 决策 (Decision)

**我们决定采用**: **方案 B —— 统一 BrowserOS 实例 + 轻量探测**

理由：

1. 方案 A 的**实例不一致**是原理性缺陷，无法通过工程手段修补 —— 探测对象错了，结果必然不可信；
2. "统一实例"让探测与执行共享同一个事实来源，这是消除假阳性的**唯一根本手段**；
3. 四态枚举（`unknown` / `needs_login` / `authenticated` / `no_publish_permission`）足以表达真实业务情况，且 `unknown` 为"不确定"提供了诚实出口，避免猜测；
4. 隐私上从"读取整个 Cookie 库"退回到"读页面特征"，与项目"会话数据零外发"的原则一致。

---

## 后果 (Consequences)

### 正面影响

- **会话状态真实可信** —— 工作台显示的"就绪"与实际预填环境一致
- **隐私承诺可兑现** —— 不再需要接触 Chrome 的 Cookie 数据库
- **架构简化** —— 登录态探测、草稿预填、指标采集三件事共用同一个 BrowserOS 实例
- 为 Phase 2 的交互式登录端点（`browser.login.*`）预留了同一实例基础

### 负面影响

- BrowserOS 实例不可用时，只能返回 `unknown`，驾驶舱信息不完整
- 探测引入导航延迟（相比直接读 SQLite 更慢）

### 风险

| 风险 | 缓解措施 |
|------|---------|
| BrowserOS 实例未启动导致全平台 `unknown` | UI 引导用户在当前 BrowserOS 实例中直接扫码登录；`unknown` 不谎报为就绪 |
| 平台验签页面结构变化导致判定失效 | 四态中的 `unknown` 作为兜底，不猜测；页面特征与网络响应双重判定 |
| Phase 2 的 `browser.login.*` 依赖未验证的 CDP 高级 API | 源文档明示"需 PoC 验证"；Phase 0 不依赖该能力（见 `risks_and_debt.md` RISK-012） |

---

## 合规性 (Compliance)

此决策的执行要求：

- 登录态探测、草稿箱预填与大屏指标采集**必须**统一由**同一个** BrowserOS MCP 实例调度
- **必须**严格返回四态 `unknown` / `needs_login` / `authenticated` / `no_publish_permission`
- ⛔ **禁止**将会话状态**退化为 boolean**（杜绝假阳性）
- ⛔ **禁止**读取或复制日用 Chrome 的 `Cookies` / `Cookies-wal` / `Cookies-shm`
- ⛔ **禁止**将会话数据（Cookie）向任何第三方服务上报
