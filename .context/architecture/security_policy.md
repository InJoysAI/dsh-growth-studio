## 🔐 认证方案 (Authentication)

### 用户认证

**N/A – 源文档未提供**（本插件无自有用户账号体系）。

本项目无用户注册 / 登录 / OAuth / JWT 流程。身份由 **DSH Desktop 宿主会话**与**平台账号自身的登录态**承载。

| 认证主体 | 方案 | 实现 |
|---------|------|------|
| **DSH 宿主 RPC** | 进程内调用，**无额外鉴权头** | `POST /api/ops`，criterion §5.1 |

| **平台登录态** | BrowserOS 实例自身用户 Profile | 不由本插件管理；经 `SessionGuard` 只读探测 |
| **DSH 自动化任务** | 宿主内工具调用 `ops_setup_schedule` | 非 RPC 方法，无独立鉴权 |

### Token 生命周期

| 项 | 规则 |
|----|------|
| **来源** | ⛔ **无内置默认值**；仅来自用户配置或环境变量 `INJOYS_MCP_ENDPOINT` / `INJOYS_MCP_TOKEN` |
| **存储** | `$DSH_HOME/ops-manager/config.json`（配置存储），明文仅供宿主内回填使用 |
| **传输** | 标准 Bearer 规范；HTTPS 强制 |
| **回填** | `config.get` 返回明文 `token` 供前端表单回填与显隐切换（见下方「令牌返回策略」） |
| **脱敏** | 日志与遥测**必须脱敏**，不得记录令牌 / Cookie / 完整正文 |

#### 令牌返回策略（重要边界）

> 当前 `config.get` **返回明文 `token`**，用于客户端表单回填与显隐切换。
> 该接口仅在**宿主内 RPC（本机进程内）**暴露，**不作为对外网络端点**。
>
> **前置条件**：若未来 RPC 可被非本机访问，**必须先**改为「只回 `hasToken: boolean`，明文另走回填专用通道」。
> 在此之前不得将该接口暴露到本机之外。
>
> **准则依据**：该明文回填属 `criterion §3.4`「令牌返回边界（本机回填例外）」明确授权的唯一例外；
> 例外按「**本机同一 DSH 实例内的受信任客户端**」界定（客户端运行在渲染进程，与宿主非同进程），
> 并**同样覆盖 `config.save` 的响应体**；不覆盖任何跨主机 / 第三方下发场景（RISK-011）。

## 🚨 敏感数据处理

### 数据分类

| 分类 | 示例 | 处理要求 |
|------|------|---------|
| **高敏感 — 会话数据** | 平台 Cookie / 会话数据 | 禁止日志；⛔ **禁止向任何第三方服务上报**（含 Injoys）；**仅存在于本地沙箱** |
| **高敏感 — 访问令牌** | Injoys 访问令牌 | 禁止日志与遥测；**仅允许发往用户配置的 Injoys 目标**用于认证（HTTPS + `Authorization: Bearer`）；⛔ 禁止向任何其他目标披露 |
| **中敏感** | 平台账号名、草稿正文、发布 URL | 日志脱敏；不记录完整正文 |
| **低敏感** | 产品名、指标数值、排期主题 | 常规保护 |

> ⚠️ **两类高敏感数据的边界不同，不可合并**：
> **Cookie 是"零外发"** —— 连 Injoys 也不能收到，因为它对本插件的任何合法集成都非必需；
> **Injoys 令牌是"受限外发"** —— 它的**唯一用途**就是向配置的 Injoys 端点证明身份，
> 因此禁止外发到 Injoys 会使合法集成**无法认证**。
> 两者的共同点是：**禁止日志、禁止遥测、禁止无关目标**。

### 会话数据零外发（铁律）

> **BrowserOS 会话在本地沙箱运行，不向任何第三方服务上报 Cookie 数据。**

| 规则 | 内容 |
|------|------|
| **禁止** | 将会话数据（Cookie）向**任何**第三方服务上报 |
| **禁止** | 拷贝并挂载整个 Chrome SQLite Cookie 库（原方案已否决，见 §会话管理） |
| **禁止** | 读取日用 Chrome 的 `Cookies` / `Cookies-wal` / `Cookies-shm` 作为会话依据 |
| **允许** | 通过 BrowserOS MCP 查询当前活跃 Tab 或后台导航至平台验签 URL，按页面特征 / 网络响应判定会话状态 |

**原方案三大根本问题（已否决，源文档 §5.1.1）**：

1. **实例不一致** —— 日用 Chrome 与 BrowserOS MCP 是完全不同的浏览器环境与用户目录，在 Chrome 探测到 Cookie **根本不能保证** BrowserOS 执行预填时已登录，导致工作台呈现「就绪」**假象**；
2. **SQLite WAL 不完整** —— 直接复制 `Cookies` 主文件未同步 `Cookies-wal` 与 `Cookies-shm`，Chrome 活跃写状态时易漏检最新 Cookie；
3. **隐私落差** —— 拷贝并挂载整个 SQLite 库会使**所有个人 Cookie 进入内存**，与「仅存在性探测」的隐私承诺存在落差。

### 脱敏规则

| 对象 | 规则 |
|------|------|
| **令牌** | 前端支持显隐切换；日志与遥测**不得记录** |
| **遥测（`tools.telemetry`）** | **必须脱敏**：不得记录令牌、Cookie 或完整正文 |
| **错误信息** | 失败需如实返回错误码与信息，但不得回显敏感凭据 |

### 假阳性防治（会话状态）

| 要求 | 内容 |
|------|------|
| **四态返回** | 严格返回 `unknown` / `needs_login` / `authenticated` / `no_publish_permission` |
| **严禁** | 退化为 boolean（criterion §5.5） |
| **理由** | 杜绝「工作台显示就绪但实际未登录」的假阳性 —— 假就绪会让用户在预填失败后才发现，浪费一轮操作 |
| **Profile 归属（§5.1.3）** | 复用**当前连接的 BrowserOS 实例**；Profile 创建/路径/隔离由 BrowserOS 或宿主管理，插件不自行读取日用浏览器 Cookie、不切换 Profile |

> ⚠️ **实现偏差（已登记，见源文档 §5.1.3）**：`src/ops-rpc.ts` 的 `browser.sessions` 在 `reuseHostBrowserProfile`（默认 true）开启时仍走读取本机浏览器 Cookie 的探测分支，**不能把 Cookie 存在当成 BrowserOS 已认证证据**；须后续提案移除该分支，`reuseHostBrowserProfile` 经兼容方案退出。

### 发布防误触（Human Confirmation）

> **自动发帖始终采取「预填至草稿箱（Draft Prefill）」策略，保留平台原生确认发布步骤，彻底杜绝误发布。**

### 闭环的契约守卫（不可省略）

> 铁律不能只写在文档里，必须由**接口契约**强制。以下校验**均位于宿主侧**，不依赖客户端自觉。

| # | 守卫 | 契约 | 错误码 |
|---|------|------|--------|
| G1 | `drafts.save` **不接受** `status: 'published'` | 服务端必须**拒绝** | `drafts/published-requires-url` |
| G2 | 回填 URL 必须为合法 `http(s)` | **须用 URL 解析器校验**，禁止用宽松正则 | `drafts/invalid-published-url` |
| G3 | 回填渠道必须属于该草稿 | 校验 `channelVariants` 成员 | `drafts/unknown-channel` |
| G4 | 多渠道仅在**全部渠道**回填后才整体 `published` | 部分回填固定 `prefilled` | —（语义规则） |
| G5 | 渠道集合变化后**必须重算状态** | 已发布草稿新增未回填渠道 → 回退 `prefilled`；须在**同一写锁内**维持不变量 | —（语义规则） |
| G6 | 渠道删除后剪除孤儿 URL | 避免残留凭据维持假「已发布」 | —（语义规则） |
| G7 | `publishedUrls` 为**服务端治理字段** | `drafts.save` 必须**忽略**调用方传入值 | —（语义规则） |
| G8 | `calendar.updateStatus` **不可**写入 `published` | 只能由 URL 回填闭环推进 | `calendar/invalid-transition` |
| G9 | 排期状态**只允许前向推进**，禁止回退 | `planned`→`drafting`→`draft_ready`→`prefilled`→`published` | `calendar/invalid-transition` |

**G1 的设计理由**（源文档 §3.2.3）：

> `published` 代表「已在平台真实发布」，其**唯一可信证据**是用户回填的**真实 URL**。
> ⚠️ **保证边界**：该"证据"来自**用户声明**。契约可校验**URL 格式合法、渠道归属、全渠道完整性**，
> 但**不能**证明页面存在、内容对应、账号归属或发布确已发生 —— ⛔ 不得把"格式合法"当作"已核实发布"。
> 若允许通用保存入口直接写 `published`，则发布闭环可被绕过，**状态会失去真实性**。
> 该守卫是**服务端**职责，**不得**仅依赖客户端不传该值。

### 状态优先级（对普通编辑入口同样生效）

状态按下列顺序判定，**前面的分支优先**：

| 优先级 | 条件 | 结果 |
|:------:|------|------|
| ① | 全部渠道有效回填 | `published` |
| ② | 存在有效回填但未齐全（部分完成） | **固定 `prefilled`** —— 普通保存**不得**降级为 `draft` |
| ③ | 完全没有发布凭据 | 使用调用方请求的编辑态（`draft` / `ready_for_review` / `prefilled`） |

> ② 的理由：**发布凭据仍在**，若允许降级，UI 状态会与已存 URL **自相矛盾**。
> 若产品确需「重新编辑后降级」，**必须先定义发布证据的保留或失效规则**，再修改本条。

### 实际遵循的隐私原则（源自架构决策，非法规驱动）

| 原则 | 落地方式 |
|------|---------|
| **数据最小化** | 会话探测**只做存在性 / 状态判定**，不导出 Cookie 内容 |

| **零外发** | 会话数据不出本地沙箱 |

| **用户知情** | 目录切换时展示三件事实提示（新目录对后续生效；在途保存写原目录；旧草稿不自动迁移） |

## AI 引用指南

当 AI 生成安全相关代码时：
1. **绝不允许**以任何形式重新引入发布工具（`ops_publish_now` 或等价物）
2. `published` 状态的唯一写入口是 `drafts.updatePublishUrl`，且须用 **URL 解析器**校验 `http(s)`
3. 令牌无内置默认值；日志与遥测**必须脱敏**
4. 会话数据**零外发**；不得读取日用 Chrome 的 Cookie 库
5. 会话状态必须四态返回，**严禁退化为 boolean**
6. 安全校验一律放在**宿主侧**，不依赖客户端
