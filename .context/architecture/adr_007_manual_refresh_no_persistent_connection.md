# ADR-007: 手动刷新 + 局部替换 + in-flight 去重（无持久连接）

**状态**: Accepted
**日期**: 2026-10-15（源文档 v1.2.0）
**决策者**: N/A – 源文档未提供

---

## 上下文 (Context)

PRD §六 要求"数据卡片支持即时刷新，无需强制重载页面"。驾驶舱需要展示跨平台指标、会话状态、排期进度等实时性有一定要求的数据。

**当前面临什么问题？**

- 如何在不重载页面的前提下更新数据？
- 是否应引入 WebSocket / SSE 实时推送，或后台定时轮询？
- 引入持久连接对宿主进程的影响是什么？

---

## 决策驱动因素 (Decision Drivers)

- **宿主进程健康**：插件运行在 DSH 宿主**进程内**，常驻连接会带来额外资源占用与生命周期管理负担
- **用户体验**：刷新不能造成整页闪烁或重复请求
- **实现复杂度**：连接生命周期、断线重连、令牌校验都需要额外设计
- **数据时效性需求**：运营数据（阅读/播放/互动）本身的更新频率是**小时级甚至天级**，无需秒级实时

---

## 备选方案 (Considered Options)

### 方案 A: WebSocket / SSE 实时推送

**描述**：建立持久连接，由宿主主动推送数据变更。

**优点**:
- 数据变更即时可见
- 无需用户手动触发

**缺点**:
- 在宿主进程内引入**常驻连接**，增加资源占用
- 需设计连接生命周期、断线重连、令牌校验方案
- **收益与需求不匹配**：运营指标更新频率低，秒级推送无实际价值
- 调试与故障排查复杂度上升

### 方案 B: 后台定时轮询

**描述**：前端按固定间隔自动调用 `workbench.overview` 等接口。

**优点**:
- 用户无需手动操作
- 无连接管理复杂度

**缺点**:
- 产生**无意义的周期性请求**（用户可能长时间不关注驾驶舱）
- 触发**重复的会话探测与指标采集**（后者会实际驱动浏览器）
- 后台持续活动，与"单机轻量插件"定位不符

### 方案 C: 手动触发 + 局部替换 + in-flight 去重（**采用**）

**描述**：

| 策略 | 内容 |
|------|------|
| **手动触发** | 刷新由用户在卡片/驾驶舱上**手动触发**对应 RPC（`workbench.overview`、`browser.sessions`、`injoys.test`） |
| **局部替换** | 前端仅做**局部状态替换**，**不整页重载** |
| **不引入持久连接** | 不使用 WebSocket / SSE，也不做后台定时轮询 |
| **单飞约束** | 同一张卡片的并发刷新请求做**去重（in-flight 合并）**，避免用户连点导致会话探测与指标采集重复执行 |

**优点**:
- **零常驻连接**，宿主进程负担最小
- 资源消耗与用户注意力**成正比**（不看不刷新）
- **避免重复的重操作**：指标采集实际驱动浏览器，去重能避免用户连点造成的重复抓取
- 实现简单，无连接生命周期管理

**缺点**:
- 用户需手动点击刷新
- 数据不是"自动最新"

---

## 决策 (Decision)

**我们决定采用**: **方案 C —— 手动触发 + 局部替换 + in-flight 去重**

理由：

1. **需求与手段匹配**：运营数据的天然更新频率（小时/天级）决定了实时推送**没有收益**；
2. **避免无意义开销**：后台轮询会在用户不关注时仍持续驱动会话探测与指标采集（后者是重操作）；
3. **宿主进程友好**：插件运行在宿主进程内，不引入常驻连接是对宿主的基本尊重；
4. **连点保护**：in-flight 合并直接解决了"用户连点导致重复采集"这一真实问题。

**远期演进的前置条件**：若后续确需准实时大盘，**须先在架构文档中补充**连接生命周期、断线重连与令牌校验方案，**再行实施**。

---

## 后果 (Consequences)

### 正面影响

- **宿主进程零常驻连接**，无额外资源占用
- 无后台请求，不产生"空转"开销
- in-flight 去重避免重复的会话探测与指标采集
- 实现与调试简单

### 负面影响

- 数据非自动最新，依赖用户手动刷新
- 用户可能忘记刷新而看到过期数据（需 UI 明确展示 `capturedAt` 或最后刷新时间）

### 风险

| 风险 | 缓解措施 |
|------|---------|
| 用户连点造成重复采集 | **in-flight 合并去重**（强制） |
| 后续有人"顺手"引入 WebSocket | criterion §3.4 明确禁止 Phase 0 引入持久连接或后台定时轮询 |
| 与 `ops_setup_schedule` 混淆，被误认为违反"禁止轮询" | **明确区分**：`ops_setup_schedule` 是 **DSH 宿主的任务调度**（到点**唤起会话**），禁止的是工作台**自建常驻连接或轮询**。二者**不可混为一谈** |
| 用户看到过期数据 | UI 展示 `capturedAt`（抓取时间）与窗口语义，明确数据新鲜度 |

---

## 合规性 (Compliance)

此决策的执行要求：

- 刷新**必须**由用户**手动触发**
- 前端**必须**仅做**局部状态替换**，⛔ 不得整页重载
- ⛔ **禁止**在 Phase 0 引入 WebSocket / SSE 持久连接
- ⛔ **禁止**在 Phase 0 引入后台定时轮询（用于刷新大盘）
- 同一张卡片的并发刷新请求**必须**做 **in-flight 去重**
- 若未来引入准实时能力，**必须**先在架构文档补充连接生命周期、断线重连与令牌校验方案

> ⚠️ **不冲突说明**：`ops_setup_schedule`（DSH 自动化任务中心注册）**不受**本条约束 ——
> 它是宿主的任务调度能力，到点**唤起会话**执行巡检，而非工作台自建轮询。
