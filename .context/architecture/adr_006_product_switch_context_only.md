# ADR-006: 产品切换仅切换生成上下文，不做数据隔离

**状态**: Accepted
**日期**: 2026-10-15（源文档 TAD v1.4.5、PRD 基线 v1.2.2 裁决）
**决策者**: N/A – 源文档未提供

---

## 上下文 (Context)

PRD §5.1.1 要求"显示当前正在运营的个人产品名，支持快速切换"。项目定位是**个人开发者的多产品推广**，因此"产品"是一个一等概念。

**当前面临什么问题？**

- 切换产品时，哪些数据应该随之切换？
- 是否应引入 `productId` 字段，对草稿、排期、指标做**多租户式数据隔离**？
- 用户的真实痛点究竟是"看到别的产品的数据"，还是"生成时用错产品的卖点与口吻"？

---

## 决策驱动因素 (Decision Drivers)

- **真实痛点对齐**：解决用户实际问题，而非想象中的越权风险
- **复杂度控制**：数据隔离会显著增加目录结构、同步与 UI 复杂度
- **实体稳定性**：新增 `productId` 会波及全部实体、契约与持久化布局
- **语义合理性**：某些数据**天然不属于产品**（如平台账号指标）

---

## 备选方案 (Considered Options)

### 方案 A: 完整数据隔离（引入 `productId`）

**描述**：为 `ContentDraft` / `CalendarItem` / `PlatformMetrics` / `SessionState` 全部新增 `productId`，切换产品时按 ID 过滤。

**优点**:
- 数据边界清晰，多产品互不干扰
- 为将来可能的团队协作预留能力

**缺点**:
- **解决的是不存在的问题**：本项目是**单用户**场景，不存在数据越权访问
- 复杂度显著上升：目录分层（`drafts/{productId}/...`）、导出/导入需带产品维度、指标归属需重新定义
- **语义错误**：`PlatformMetrics` 属于**平台账号**而非产品 —— 同一个 B站账号既发 A 产品也发 B 产品，按产品切分指标会**丢失真实总量**
- `SessionState` 属于 BrowserOS 实例与平台账号，**与产品无关**
- 每次切换产品都要重载全部视图，反而降低体验

### 方案 B: 仅切换生成上下文（**采用**）

**描述**：`defaultProduct` 仅决定：

| 维度 | 是否随产品切换 | 说明 |
| :--- | :---: | :--- |
| Injoys 知识库检索范围 | ✅ 切换 | 按 `defaultProduct` 检索对应产品的卖点/调性/Changelog |
| AI 生成上下文与默认产品名 | ✅ 切换 | 生成物料的身份与口吻随之变化 |
| 指标（`PlatformMetrics`） | ❌ 不切换 | 指标属于**平台账号**而非产品，全局共享 |
| 排期（`CalendarItem`） | ❌ 不切换 | 与草稿同为全局工作区 |
| 草稿库（`ContentDraft`） | ❌ 不切换 | 草稿已通过 `topic`/`title` 表达其所属产品 |
| 会话状态（`SessionState`） | ❌ 不切换 | 会话属于 BrowserOS 实例与平台账号 |

**优点**:
- **直击真实痛点**："生成时用错产品的卖点与口吻"
- 零额外复杂度：实体不新增字段，持久化布局不变
- 语义正确：指标留在平台账号维度，不丢失真实总量
- 草稿通过 `topic` / `title` **自然表达**所属产品，无需强制字段

**缺点**:
- 无法按产品过滤草稿与排期（个人场景下可用 `topic` 检索替代）
- 若未来真需要隔离，需重新设计

### 方案 C: 混合 —— 生成上下文 + 仅草稿隔离

**描述**：草稿按产品分目录，其余全局共享。

**优点**:
- 一定程度区分内容资产

**缺点**:
- 隔离不彻底（排期仍全局），语义模糊
- 引入目录分层却无明确收益
- 排期关联的 `documentId` 跨产品跳转会让 UI 复杂化

---

## 决策 (Decision)

**我们决定采用**: **方案 B —— 仅切换生成上下文，不做数据隔离**

理由：

1. **本项目定位是个人开发者多产品推广的轻量场景**，产品切换的核心痛点是"生成时用错产品的卖点与口吻"，**而非数据越权隔离**；
2. 引入强制隔离会**显著增加目录与同步复杂度而无对应收益**；
3. 方案 A 在**指标维度上是语义错误的** —— 指标属于平台账号，按产品切分会产出错误的"全网总量"，直接违反"数据真实性"质量目标；
4. 草稿已经通过 `topic` / `title` 表达了其所属产品，无需冗余字段。

---

## 后果 (Consequences)

### 正面影响

- **实体保持简洁**：`ContentDraft` / `CalendarItem` **不新增 `productId`**
- **不引入多租户隔离**，持久化布局、同步逻辑与 UI 均保持简单
- **指标语义正确**：仍按平台账号聚合，全网总量可信
- 切换产品为**轻量操作**（仅影响后续生成），无需重载视图

### 负面影响

- 无法按产品维度过滤草稿 / 排期列表
- 多产品内容混在同一工作区，依赖 `topic` / `title` 人工区分

### 风险

| 风险 | 缓解措施 |
|------|---------|
| 用户误以为切换产品会隔离数据 | 语义在架构文档与 criterion §5.5 中明确定义：**仅切换生成上下文** |
| 后续需求变化需要真隔离 | **前置条件已写入**：须**先**在 PRD 定义多产品数据模型与切换后的数据可见性规则，**再**扩展本表与实体 |
| 生成时仍用错产品 | 知识库检索范围随 `defaultProduct` 切换；生成上下文明确带上产品身份 |

---

## 合规性 (Compliance)

此决策的执行要求：

- `defaultProduct` **仅**影响 Injoys 知识库检索范围与 AI 生成上下文
- ⛔ **禁止**为 `ContentDraft` / `CalendarItem` 新增 `productId` 字段
- ⛔ **禁止**引入多租户数据隔离
- 指标（`PlatformMetrics`）、排期（`CalendarItem`）、草稿（`ContentDraft`）、会话（`SessionState`）**必须全局共享**
- 若未来确需数据隔离，**必须先在 PRD 定义**多产品数据模型与切换后的数据可见性规则，再扩展语义表与实体
