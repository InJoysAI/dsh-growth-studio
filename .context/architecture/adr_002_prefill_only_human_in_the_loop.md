# ADR-002: 仅预填 + 人工发布 + URL 回填闭环（Human-in-the-Loop）

**状态**: Accepted
**日期**: 2026-10-15（源文档 v1.2.0）
**决策者**: N/A – 源文档未提供

---

## 上下文 (Context)

工作台的核心价值之一是"把内容自动送到平台草稿箱"。这自然引出问题：**能否让 AI 直接完成发布？**

若允许 AI 点击"发布 / 群发"按钮，一旦发生幻觉（内容错误、发错平台、重复发布），后果**不可撤销** —— 公众号群发、B站投稿、X 推文都会立即对真实受众可见。

同时需要一个机制来知道"到底发出去了没有"，以便驱动指标追踪与复盘。

**当前面临什么问题？**

- 自动化发布的**风险敞口**远大于其带来的效率收益；
- 但完全不追踪发布结果，又无法形成"发布 → 指标 → 复盘"的闭环；
- "人工核验"是一个**动作**而非**状态**，系统无法直接观测。

---

## 决策驱动因素 (Decision Drivers)

- **安全第一**：彻底消除 AI 幻觉引发的不可控群发风险
- **状态真实性**：系统记录的"已发布"必须可信
- **效率收益**：仍要消除"逐平台复制粘贴"这一最大痛点
- **可观测性**：需要某种系统可验证的信号来确认发布发生

---

## 备选方案 (Considered Options)

### 方案 A: AI 全自动发布（含点击发布按钮）

**描述**：预填完成后由 AI 直接点击平台原生发布按钮完成发布。

**优点**:
- 端到端零人工，效率最高

**缺点**:
- **风险不可接受** —— 幻觉导致的错误群发**不可撤销**
- 平台侧可能触发风控 / 封号
- 违反"保留平台原生确认发布步骤"的防误触原则
- 失去人工对内容质量的最后一道把关

### 方案 B: 仅预填 + 人工发布 + URL 回填闭环（**采用**）

**描述**：
1. 从**所有**工具白名单、RPC 端点和文档中**彻底删除**正式发布工具 `ops_publish_now`；
2. 预填**止步于**平台原生"保存为草稿"按键（公众号：标题/作者/正文；B站：标题/简介/标签/分区）；
3. 预填完成后向工作台返回**草稿直达链接**；
4. 用户在浏览器中完成最终人工核验并点击发布；
5. 用户将**正式发布后的真实 URL 回填**至工作台，草稿状态推进为 `published` 并关联指标追踪。

**优点**:
- **移除专用发布入口**（发布类工具不存在 → 无法经专用入口构造调用），发布由人工完成
- 消除了"逐平台复制粘贴"这一最大痛点，效率收益保留
- 保留人工对内容的最终把关
- URL 回填为"已发布"提供了**唯一可信证据**

**缺点**:
- 仍需人工完成最后一步发布（**这是有意的取舍**）
- 用户需手动回填 URL（一次性的低摩擦操作）

### 方案 C: 预填 + 定时自动发布确认

**描述**：预填后进入倒计时，用户在倒计时内未取消则自动发布。

**优点**:
- 兼顾"不阻塞"与"有把关"

**缺点**:
- 本质仍是自动发布，**风险敞口未消除**（用户可能不在场）
- 引入定时器与调度复杂度
- 与"保留平台原生确认发布步骤"原则冲突

---

## 决策 (Decision)

**我们决定采用**: **方案 B —— 仅预填 + 人工发布 + URL 回填闭环**

理由：

1. 方案 A/C 的风险与收益**不成比例** —— 一次错误群发的声誉损失远超自动化节省的时间；
2. **能力移除比权限控制更强**：与其"允许但校验"，不如让发布工具**不存在于 catalog**，使经**专用发布入口**的调用**无法构造**；但仍依赖业务守卫（见下方「保证边界」）；
3. 铁律不能只写在文档里，**必须由接口契约强制**（见下方"合规性"）；
4. URL 回填既解决了"如何知道已发布"，又把"已发布"从**不可观测状态**变成**可记录、可追溯的状态** ——
   用户回填的 URL 是本系统**唯一可得的**发布证据（源文档 §3.2.3 表述为「唯一可信证据」）。

> ⚠️ **保证边界（不得夸大）**：上述"证据"的**权威性来自用户声明**，而非系统的独立核实。
> 当前契约能校验的是：**URL 格式合法（`http(s)`，经解析器）、渠道属于该草稿、全渠道完整性**。
> 它**不能**证明：目标页面真实存在、内容与草稿对应、账号归属正确、或发布确实已发生。
> 因此**不得**把"URL 格式合法"等同于"发布已核实"。
> 若未来需要平台侧自动验真，须**另行提案**并定义契约（含网络访问与失败语义），不得在本 ADR 内推定。

---

## 后果 (Consequences)

### 正面影响

- **移除专用发布入口** —— 发布类工具恒不存在于 catalog；但**不据此宣称零风险**（细粒度行为拦截未定，见 ADR-009 边界与源文档 §3.12.6）
- 状态真实性有据可依 —— `published` 由用户回填的 URL 驱动（**证据来自用户声明**，见上方「保证边界」）
- 人工保留质量把关，符合谨慎运营习惯
- 发布 URL 同时成为后续指标追踪与内容复盘的锚点

### 负面影响

- 无法实现"无人值守发布"
- 需要用户养成回填 URL 的习惯（UI 需提供便捷入口）
- 多渠道草稿需**全部**回填才推进整体状态，用户可能对"为什么还是 prefill"产生疑问（需 UI 文案解释）

### 风险

| 风险 | 缓解措施 |
|------|---------|
| 用户用空值 / 占位符"骗过"状态推进 | URL 必须经 **URL 解析器**校验为合法 `http(s)`，**禁止**宽松正则 |
| 通用保存入口被用来直接写 `published` | `drafts.save` 传入 `published` **一律拒绝**（`drafts/published-requires-url`） |
| 部分渠道发布被当成全部完成 | **全渠道不变量**：仅在全部渠道回填后才整体 `published`；部分回填固定 `prefilled` |
| 调用方伪造发布凭据 | `publishedUrls` 为**服务端治理字段**，`drafts.save` 必须忽略传入值 |
| 渠道移除后残留 URL 维持假"已发布" | **孤儿清理**：不再对应任何当前渠道的 URL 被剪除；渠道集合变化须**在同一写锁内**重算状态 |

---

## 合规性 (Compliance)

此决策的执行要求：

- ⛔ **禁止**以**任何形式**重新引入 `ops_publish_now` 或任何发布类工具 / RPC 端点
- 预填流程**必须**止步于平台原生"保存为草稿"
- `published` **只能**经 `drafts.updatePublishUrl` 写入
- 回填 URL **必须**用 URL 解析器校验（禁用宽松正则）
- 回填渠道**必须**属于该草稿的 `channelVariants`，否则 `drafts/unknown-channel` 且**不写盘、不递增版本**
- 多渠道草稿**必须**在**全部渠道**回填有效 URL 后才整体 `published`
- 上述校验**必须**位于**宿主侧**，**不得**仅依赖客户端
- `ops_setup_schedule` 注册的巡检任务执行时仍**必须**受本铁律约束
- ⛔ **禁止**把 URL 格式校验表述为"平台真实性证明" —— 证据来源是**用户声明**；自动化验真须另行提案
