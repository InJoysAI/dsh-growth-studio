# ADR-008: 草稿版本采用独立快照存储与非破坏性恢复

**状态**: Accepted
**日期**: 2026-10-15（源文档 v1.2.0）
**决策者**: N/A – 源文档未提供

---

## 上下文 (Context)

PRD §5.4.1 要求"支持草稿历史查看、手动编辑正文、标题/标签微调与**多版本存盘**"。

`ContentDraft` 已有 `version: number` 字段，每次 `drafts.save` 自增。

**当前面临什么问题？**

- **`version` 自增只表示当前版本号，不等于保存了历史内容** —— 仅靠该字段无法回看旧版本；
- 用户"恢复旧版本"时，若直接覆盖当前内容，会**丢失恢复前的状态**，操作不可逆；
- 需要决定历史内容的存储布局、原子性保证、保留策略与删除语义。

---

## 决策驱动因素 (Decision Drivers)

- **可回溯性**：必须能读取任意历史版本的**全文**
- **可逆性**：恢复操作本身应可被再次恢复
- **向后兼容**：`drafts.get` 的既有语义（返回当前版本）不应改变
- **原子性**：不得出现"版本号已增但快照缺失"的不一致状态
- **存储成本**：个人开发者场景下落盘量有限

---

## 备选方案 (Considered Options)

### 方案 A: 仅靠 `version` 字段（不存历史）

**描述**：`version` 只是计数器，覆盖式写入当前版本。

**优点**:
- 实现最简，零额外存储

**缺点**:
- **无法满足 PRD §5.4.1 的"多版本存盘"要求**
- 用户无法回看或恢复历史内容

### 方案 B: 单文件内嵌历史数组

**描述**：把全部版本存入 `{id}.json` 的一个数组字段。

**优点**:
- 单文件，无目录管理

**缺点**:
- **文件体积随版本线性增长**，每次读取当前版本都要载入全部历史
- 写入需重写整个文件，原子性与性能都变差
- `drafts.get` 的读取成本被历史内容拖累

### 方案 C: 独立版本快照目录 + 非破坏性恢复（**采用**）

**描述**：

```text
$DSH_HOME/growth-studio/drafts/
├── {id}.json                    # 当前版本（含 version 字段，读路径不变）
└── {id}.versions/
    ├── v1.json                  # 版本 1 的完整内容快照
    ├── v2.json                  # 版本 2 的完整内容快照
    └── ...
```

**优点**:
- **读取路径不变** → 对既有接口**向后兼容**
- 快照按需读取（`drafts.getVersion`），不影响 `drafts.get` 性能
- 每个快照独立文件，可沿用"临时文件 + rename"的原子保证
- 恢复操作可做**非破坏性追加**

**缺点**:
- 引入子目录，需注意 `drafts.list` 不得把子目录误当草稿项
- 文件数量随版本增长

---

## 决策 (Decision)

**我们决定采用**: **方案 C —— 独立版本快照目录 + 非破坏性恢复**

### 设计要点

| # | 要点 | 内容 |
|---|------|------|
| 1 | **写入时机** | `drafts.save` 每次成功写入新版本时，**同时**将该版本完整 `ContentDraft` 写入 `{id}.versions/v{version}.json`。当前版本文件与快照在**同一串行写锁内**完成，避免"版本号已增但快照缺失" |
| 2 | **原子性** | 快照同样采用"**临时文件 + rename**"写入，与当前版本文件保持一致 |
| 3 | **保留策略** | Phase 0 **保留全部版本**（个人开发者场景单草稿版本量有限），**不自动淘汰** |
| 4 | **读取路径** | `drafts.get` 语义不变（返回当前版本），历史读取走 `drafts.getVersion`，二者互不影响 → **向后兼容** |
| 5 | **删除语义** | `drafts.delete` **级联删除** `{id}.json` 与整个 `{id}.versions/` 目录 |
| 6 | **一致性校验** | `drafts.listVersions` 的版本号集合应等于 `v{n}.json` 文件集合；若当前版本号高于最大快照号（历史数据由旧版本代码写入），应**如实返回已有快照**并给出可用版本列表，**不得伪造缺失版本** |

### 非破坏性恢复语义

> **不做破坏性回滚**。恢复操作把目标版本内容作为**基础**，**追加为新版本**（`version` 继续自增），
> 历史版本**一律保留**，因此**恢复操作本身也可被再次恢复**。

**理由**：用户点"恢复"通常是在试错（"上一个版本好像更好"）。若采用覆盖式回滚，用户一旦恢复错版本就**永久丢失**恢复前的内容，反而制造了新的数据丢失场景。

---

## 后果 (Consequences)

### 正面影响

- **完整可回溯**：任意历史版本均可读取全文（`drafts.getVersion`）
- **操作可逆**：恢复不丢当前内容，恢复本身可再恢复 —— **消除试错成本**
- **向后兼容**：`drafts.get` 读取路径与语义不变，既有客户端无需改动
- **原子保证一致**：当前版本与快照在同一写锁内完成，且都用临时文件 + rename
- **存储可控**：单草稿版本量有限，全量保留的成本可接受

### 负面影响

- 磁盘占用随版本数线性增长（Phase 0 有意接受）
- 引入子目录，`drafts.list` 需显式避免把 `{id}.versions/` 当作草稿项
- `drafts.delete` 必须实现级联删除，否则会残留孤儿快照

### 风险

| 风险 | 缓解措施 |
|------|---------|
| `drafts.list` 误把版本子目录当作草稿项 | 源文档明确提示：`list` 只扫描目录下的**文件**，实现时须避免把版本子目录误当作草稿项 |
| 版本号与快照不一致（旧代码写入的历史数据） | 规则 6：**如实返回**已有快照与可用版本列表，⛔ **不得伪造缺失版本** |
| 快照丢失导致"版本号已增但无法回看" | 规则 1：当前版本与快照在**同一串行写锁内**完成 |
| 删除草稿后残留快照占空间 | 规则 5：级联删除整个 `{id}.versions/` 目录 |
| 未来版本量过大 | 若需上限，应**先在 PRD 定义**保留条数与用户可见的淘汰提示，再引入（Phase 0 不做） |

---

## 合规性 (Compliance)

此决策的执行要求：

- `drafts.save` **必须**在同一串行写锁内同时写当前版本与快照
- 快照**必须**采用临时文件 + rename 的原子写入
- `drafts.get` **必须**保持"返回当前版本"的既有语义
- `drafts.restoreVersion` ⛔ **必须不做破坏性回滚** —— 只能追加为新版本
- `drafts.delete` **必须**级联删除 `{id}.json` 与 `{id}.versions/`
- `drafts.listVersions` **必须**如实返回已有快照，⛔ 不得伪造缺失版本
- `drafts.list` ⛔ **不得**把版本子目录当作草稿项
- Phase 0 **必须**保留全部版本，⛔ 不得自动淘汰
